# 06 Python 版與規格的差異

01 到 05 是要重製的遊戲。這一章是讀現有程式時會踩到、但 Godot 不該照抄的行為。每一項都標了「舊行為」與「重製時」。

若某個實驗必須重放已寫入 `raw_logs` 的對局特徵，只在特徵那一項改回舊行為，其餘仍用新規格。

## 對局流程

### bot 摸牌後什麼都不做

`MahjongGUIEnv` 在 `player_take_on_draw_action` 裡，bot 的 `chosen_action` 被設成 `None`，然後落到打牌。bot 不會自摸、不會暗槓、不會加槓。人類可以。

重製時：bot 有合法自摸就自摸；暗槓與加槓用 `decide_kong` 的花色限制。否則舊 bot 幾乎只靠食出得分，和人類不是同一個遊戲。

### 狀態用連續 `if` 串在一起

同一個 `update_game_state` 裡，後面的 `if` 會看見前面剛改掉的狀態。全 bot 時，一幀裡會完成摸牌、放棄摸牌動作、打牌、詢問叫牌。遇到 bot 選擇明槓時函式直接 `return`，這一幀不再處理後面的玩家。

重製時：一個狀態一次只做一件事。三家都回答完才進入結算。不要在選中槓的當下 return 而漏掉尚未回答、但可能胡牌的玩家。

### 人類吃牌有多種選法時，後面的玩家不再被問

`player_choose_chow_tiles` 選完會把狀態設成 `processing_call_queue`。對家若也能胡或碰，這一幀不會被記錄。

重製時：先收齊三家的選擇，再用胡、槓、碰、吃的優先權結算。

### 換局迴圈看起來有三層，實際靠 `end_round` 在下一幀被清掉

`MahjongGUI.run` 的中層 `while not end_round` 在第一局結束後就不會再進去，因為最內層只看 `end_game`。下一幀的 `round_reset` 把 `end_round` 設回 false，所以整場仍會打完。這是碰巧能跑完，不是要保留的結構。

重製時：用 `ending_round` → 下一局或下一圈，外層只等 `ending_game`。

### 第一局開始前多轉了一次座位

`add_players` 洗一次牌，`start_game` 再洗一次並指定座位，接著第一次 `round_reset` 又把座位左輪。第一局的莊家不是 `start_game` 剛指定的那個人。

重製時：開賽洗一次座位，第一局就用這份座位。之後每局結束才左輪。

## 計番

### 圈風番永遠是東

`FaanCalculator.round` 只在建構時是 0。換圈時沒有人把 `wind` 寫進去。`round_wind()` 因此只認 classId 28。門風會在 `set_position` 時更新，這部分是對的。特徵向量的 `current_wind` 用的是環境上的 `wind`，和計番器不一致。

重製時：每局把圈風寫進計番器。南圈碰南風要有圈風 1 番。

### 搶槓、天胡、地胡不會發生

`robbing_additional_kong_flag` 只會被設成 false。`havenly_hand` 與 `earthly_hand` 的判定是 `None`，`check_faan_match` 會跳過。加槓不會詢問其他家。

重製時：依 [01-rules.md](01-rules.md) 補上。若要先交付可玩版本，這三個番保持不出現，但不要在別的番種裡留下「永遠 false」的旗標還繼續當自摸處理。

### 全字牌會同時變成清一色與混一色

`pure_suit` 只要求每一張 `tile_suit` 相同。字牌的花色都是 `z`，所以字一色會得到清一色 7 番。`clean_hand` 同樣會通過，再加混一色 3 番。再加上字一色 10 番與對對胡，列表很長，但 `min(total, 10)` 之後分數仍是 10 番那一列。

重製時維持這個列表，才和現有 `winning_faan` 一致。若論文裡的定義是「清一色不能有字、混一色必須有數牌」，可以在這兩個函式裡把「全部都是 `z`」判成失敗。分數不會變，番種名稱會變。

### 風的槓不算進小四喜、大四喜

`little_4_winds_hand` 與 `great_4_winds_hand` 看副露時只接受 `pong`，不接受 `kong`。白板、發、中的番與大三元有把槓算進去。

重製時：四種風的碰和槓都算「有這組風」。

### 手牌裡的字牌可以被面子函式看成順子

`check_tuple_type` 只看點數連續與花色相同。東 1、南 2、西 3 會得到 `chow`。胡牌搜尋的順子迴圈停在 classId 27，所以這種組合不會讓人胡牌。

重製時：順子限定萬筒索。

### 測試註解的三元牌顏色是反的

`TestFaanCal` 的註解把 32 寫成紅中、33 寫成白板。牌表、Unicode 與 `white()` / `green()` / `red()` 的 classId 才是對的：32 白、33 發、34 中。

## 叫牌與 bot

### 「能不能吃」和「有哪些吃法」不一致

`check_possible_calls` 只拿同花色、排序後相鄰的兩種點數去試。手牌同時有 1、2、3 萬，別人打 2 萬時，相鄰組合是 1-2 與 2-3，都配不成順，吃的按鈕不會出現。`get_chow_options` 會看到 1 與 3。

重製時：能不能吃，以 `get_chow_options` 非空為準。

### heuristic 選出的吃牌組合被丟掉

`decide_chow` 回傳建議的兩張點數，`BotPlayerGUI.decide_call_action` 只把動作字串回傳。環境再用 `get_chow_options()[0]`。

重製時：heuristic bot 繼續用選項列表的第一組，與現有 bot 相同。人類自己選。不要讓政策回傳的那組只在測試裡有效、對局卻用另一組，除非兩處改成同一組。

### 人類點空處仍可能改到手牌

`waiting_discard` 在滑鼠事件裡，就算沒點到牌，也會用現有的 `discard_buffer` 去濾手牌，並清掉自摸與連槓旗標。

重製時：沒點到牌就什麼都不做。

### 明槓把同一 classId 全部移出

判定已經要求手牌正好 3 張，所以正常不會多拿。若以後放寬判定，要只取 3 張，第 4 張留在手裡。碰的實作有把多餘張數放回，明槓沒有。

## 特徵與 log

### 對家的吃牌 21 維用錯 index

自己、下家、上家用「最小 classId → 0..20」的表。對家用 `最小 classId - 1`，7 索那類順子會寫到下家碰牌的區間。

重製時：四家都用 0..20 的表。只有在比對舊模型的輸入時才複製這個 bug。

### 食出那一筆的三家副露是相對打出者

胡牌 log 的 `player_id` 是勝者，但 `next` / `opposite` / `previous` 用的是當時的 `current_player`，也就是打出者。碰、吃、明槓在寫 log 之前已經把 `current_player` 改成呼叫者，所以那幾筆是相對行動者。

重製時：每一筆都相對 `player_id`。文件裡的訓練說明也按這個意義。

### bot 的 pass 多半沒有紀錄

人類放棄叫牌會寫 `pass`。bot 把 offers 清掉，不寫。

重製時：建議都寫。舊訓練程式若把「沒有 pass 紀錄」當成負樣本的來源，要先確認再改。

### Discard 模型拿掉的是動作牌那一段

426 維是 `features[:392] + features[426:]`。不要改成拿掉別的 34 維。

### 門檻是 logit > 0.5

沒有 sigmoid。0.5 不是機率 0.5。匯出 ONNX 時保持最後一層的線性輸出，Godot 用同一個比較。

## 畫面

四家手牌是由下往上的橫列，不是圍著桌子轉 90 度。有人類時其他人的手牌不畫，副露仍畫。牌圖路徑在 `assets/*.png`，倉庫裡沒有圖檔。

重製時：規則與快照分開之後，第一版可以沿用直排。四方桌只改 `TableView`。

## 建議不要修進規則裡的既有設計

這些是設計，不是 bug：

- 無花牌、無死牌牆、槓從活牆補。
- 三番起糊，10 番封頂。
- 食出一家付清，自摸三家分。
- 胡牌不連莊，東南西北各四局。
- 只有下家可以吃。
- 暗槓算副露，因此破壞門清，也使「四暗刻」只在四組刻子都還留在手牌時成立。
- 分數可以是小數與負數。
- 棄牌池的特徵不含此刻尚未被叫走的那張牌。
